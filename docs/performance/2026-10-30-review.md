# Performance review — OfferPath 2.4.3

Reviewed the React page/query lifecycle, shared API transport, workspace gateway,
SQLite access and indexes, dashboard/triage reads, sourcing snapshots and matching,
calendar/process projection, payments, follow-up decoration and production bundles.
Measurements use isolated synthetic data; no production mail or credentials were
used. They describe the tested paths, not an end-to-end production SLA.

## Reproduced and corrected

- Calendar and process lists resolved sources once per displayed event. Each call
  scanned all retained events, producing quadratic work and three SQL reads per
  displayed booking. Bulk resolution now reads events and sources once and only
  compares candidates with matching start times. Retained copies and source order
  remain intact. Account projections exclude provider-deleted source copies.
- Empty process pages scanned saved messages twice despite having no organization
  that could use them. Empty pages now skip both scans. Domain-only process matching
  no longer materializes full mail bodies into Python; explicitly configured manual
  name matching still reads bodies, preserving its documented behavior.
- Header focus/check-start events could overlap pending status requests, while a
  running-state transition restarted the polling effect. Polls are now serialized
  and the next interval uses the latest received running state.
- General page reads had no client deadline, including during response-body parsing.
  Read requests now abort after 30 seconds with a clear error and release timers
  and cancellation listeners. Explicit caller cancellation is preserved. Mutating
  requests retain their existing completion behavior rather than being blindly
  retried after an ambiguous timeout.
- Triage was eagerly included in the app shell even for sign-in, bidder and other
  routes. It now uses the same lazy route boundary as the other pages.

The preceding 2.4.2 fix also prevents overlapping spreadsheet refreshes from
invalidating slow successful responses and cancels obsolete sheet requests.

## Measurements

A temporary SQLite database with 500 distinct bookings and 500 source records:

| Source resolution | Queries | Elapsed |
| --- | ---: | ---: |
| Previous per-event calls | 1,500 | 2.6859 s |
| Bulk calls | 2 | 0.0145 s |

Both produced the same ordered source records. The approximately 185x improvement
applies to this isolated source-resolution workload, not every calendar request.
Regression tests assert a constant query count rather than machine-dependent timing.

The main production JavaScript entry decreased from 512.25 kB (161.06 kB gzip)
to 492.85 kB (155.67 kB gzip). Triage is fetched separately when its route opens.

## Boundaries

Existing gateway HTTP connection pooling, immutable hashed asset caching, SQLite
WAL, received-date/latest-classification indexes, route splitting and bounded
triage/dashboard result sets were retained. No shared cache of private workspace
responses or permission results was introduced. Outlook/provider latency, Windows
host disk/CPU utilization, VPN/tunnel connectivity and concurrent production load
require measurements on the hosting PC; these cannot be inferred from local tests.
